# Loop Method — 分解、驗證、決策

你在一個量化交易專案裡工作。真錢在跑、排程曾被洗空三次、回測過擬合是頭號職業病。
這份方法論的核心只有一句：**宣稱之前先有證據；做事的人不當裁判。**

## 一、任務分解

1. **動手前先讀記憶**（不可跳）：`LOOP_MEMORY.md`（本檔同層規則）、auto-memory 的 `MEMORY.md` 索引、若是策略研究則加 `strategies_research/LESSONS.md`。目的：不重試已證明的死路、不把已知事故當新謎題。
2. **先定義「完成」再開工**：完成條件必須是一行指令能判 PASS/FAIL 的東西（pytest 全綠、對帳誤差=0、OOS 門檻全達標）。如果寫不出這行指令，第一個子任務就是「先建判準」，而不是開始做事。
3. **五階段骨架**：探索 → 規劃 → 執行 → 驗證 → 迭代。探索階段寧可多花時間讀現有代碼與 log，也不要憑印象規劃 — 這個 repo 的坑（時區 UTC vs TST、試撮假 tick、stale .pyc、雙格式歷史 K 線）都是「憑印象」踩出來的。
4. **切塊原則**：每個子任務要有獨立可驗證的產物。互相獨立的子任務並行（開 subagent），有依賴的串行。驗證用的 subagent 和執行的 subagent 永遠分開。
5. **先 smoke 後定版**：任何昂貴驗證先跑最小版本確認管線通（5-trial 先於 60-trial、單日 replay 先於兩週 replay）。smoke 漂亮、定版崩 = 過擬合或僥倖，不准當成功。
6. **複雜度爆表時停下重規劃**：發現實際結構和規劃假設不符（檔案格式不同、API 行為不同），回到規劃階段改計畫，不要硬改代碼遷就錯誤假設。

## 二、驗證習慣

1. **裁判獨立**：自己改的代碼不自己打分。用獨立 context 的 subagent 驗證，或用機械判準（測試、diff 對帳、門檻指令）。
2. **證據先於宣稱**：說「修好了」之前必須實際跑過驗證指令並看到輸出。失敗就照實報失敗並附輸出原文；跳過就說跳過。禁止虛假的「完成」。
3. **判生效看行為不看磁碟**：rsync 上去的檔案 ≠ 跑的代碼（stale .pyc 事故）。驗證修復要看行為改變（log 出現新字樣、行為不再復現），不是看檔案內容對了。
4. **數字先查證再講**：任何數字（保證金、PF、行數、日期）講出口前先跑指令確認。讀不到就說讀不到，不編。user 質疑你的數字時，預設是系統錯了，先查再辯。
5. **診斷異常先驗基本面**：報「漏排程/漏推送」之前先確認 — 今天星期幾？休市日？cron 的 UTC 換算成台灣時間對嗎？（7/4「漏推送」誤診 = 那天是週六。）
6. **量化鐵律 — 裁判必須是 OOS**：任何策略/參數迭代迴圈，終止條件只能是 walk-forward OOS + 跨合約門檻，絕不能用同一段回測的 PF。用 in-sample 當裁判的迴圈是自動過擬合機器，跑越久越毒。同理：不憑單筆 live 結果改 OOS 驗過的策略。
7. **新建的自動化，驗收要包含「明天它自己還會不會跑」**：建完排程/觸發器當場看 Next Run 是不是明天；驗收排到「明天」而明天臨時休市時，驗收順延而不是消失。（2026-07-16 教訓：sweep_health_check 建成一次性觸發器，跑滿 23 小時永久停，Ready + exit 0 全綠地靜默死了 6 天。）

## 三、決定下一步

1. **驗證失敗 → 讀錯誤原文**（完整 traceback / log 段落），定位根因，修，重驗。禁止不看錯誤就重跑同一指令。
2. **同型失敗連續 3 次 → 停**。寫進 LOOP_MEMORY「未解決」區並升級給人。繼續槌下去只會燒 token 和製造更多半成品。
3. **失敗要提煉，不只記錄**（五層）：記下失敗 → 調查為何失敗 → 用數據驗證成因（不是猜）→ 提煉成通用規則 → 之後查規則而非重新推導。只做到第 1 層的記憶檔沒有價值。
4. **每輪結束更新 LOOP_MEMORY.md**，相對日期一律寫成絕對日期。
5. **做完 ≠ 收工**：收工前自檢 — 完成條件那行指令真的跑了嗎？綠的嗎？有沒有承諾了但沒做的事殘留在最後一段話裡？
6. **修 bug 必修 class，不只修 instance**：事故根因確認後，把根因抽象成可 grep 的 pattern（寫死月份合約碼、一次性觸發器、`crontab -l | grep -v | crontab -` 自刪管線、cp950 解碼…），對全 repo＋全排程掃同型 — 活路徑命中全修，研究腳本標註「故意」。今天沒發病的同型雷，事故驅動的檢查永遠碰不到：2026-07-16 Astruct 寫死 MXF202607，在錄製器換月事故「都修了」的**隔天**爆，就是只修了 instance。**宣稱「都修正了」的合法範圍 = 實際掃過的範圍**，說出口前先問自己：我掃了哪裡、用什麼 pattern。

## 四、迴圈記憶協定

repo 根目錄維護 `LOOP_MEMORY.md`，三個區塊：

- **已測試**：做過什麼實驗/修復、結果如何（含失敗）
- **已驗證**：確認過的事實（有指令輸出背書的才算，假設不算）
- **未解決**：還沒試的方向、卡住的問題、升級待人決策的事

規則：**每輪開始前讀它，每輪結束前更新它。** 條目移動方向只有「已測試 → 已驗證」（用數據確認後）或留在未解決。

## 五、本專案紅線（迴圈永遠不准自動做）

| 紅線 | 原因 |
|---|---|
| 真錢下單 | 不可逆 |
| live 修復的部署/重啟/上線（**repo 內改 live 引擎代碼+測試 = 可以迴圈**） | 生產重試=真錢；持倉中的重啟要人審；修法生效看 live 行為不看磁碟 |
| VPS crontab 任何寫入 | 已洗空三次；鐵律在專案 CLAUDE.md，只准照那個流程且人審 |
| rsync 部署到 VPS | 迴圈可以產出部署包，但推上去那一下人按 |
| 刪除/覆蓋非自己建的檔案 | 先看內容，與描述不符就上報 |
| 憑單筆 live 改策略參數 | 見二-6 |

修 engine bug 的迴圈有一條加分義務：**修復必須附一支覆蓋該事故的回歸測試**（`TMFtrader-src/tests/` 既有 22 支全是這樣來的），測試綠了才算完成。
