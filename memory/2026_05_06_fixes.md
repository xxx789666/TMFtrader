**已修復 2026-05-06**：

## ① Backtest workers 污染 production `risk_state.json`

**症狀**：log 顯示 `[Persist] 載入風控狀態` 在同一秒內出現 5+ 個不同的 peak（219K/254K/247K/259K/251K），最後寫入 `risk_state.json` 的 peak=251,800 vs 實際 paper 帳戶 ~200,000 → 明早日盤啟動就會看到 21% 假回撤、整天空轉（即 paper_trading_peak_equity_bug 的第三層 root cause）。

**根因**：`risk/manager.py:RiskManager.__init__` 無條件 `load_risk_state()`，`on_trade_closed → _save_state` 無條件 `save_risk_state()`。`backtest/engine.py` 和 `backtest/fast_engine.py` 都用同個 `RiskManager`，並行 worker 跑時用整檔覆寫 → last writer wins。

**修法**：`RiskManager(profile, persist=True)` 加 kwarg，backtest 兩個 engine 改 `persist=False`，`_save_state` 開頭 `if not self._persist: return`。Tests 也順手改用 `persist=False`。
**Why:** 這是繼「日夜盤共用 state file（已用 _night suffix 修）」「paper 重啟 peak 重置（已修）」之後，第三個 peak_equity 污染來源。  
**How to apply:** 任何模組要 instantiate `RiskManager` 而不在 live engine 上跑，必須傳 `persist=False`。Pytest 18 全綠，`risk_state.json` 已重置為 `peak=212180`、`risk_state_night.json` 為 `peak=200000`。

## ② Daily performance journal 日夜盤碰撞（最嚴重）

**症狀**：5/4 兩筆 TMF 交易只有 1 筆進 `2026-05-04_live.json`；5/5 09:01 TMF +1,920 完全沒進 journal；每日 `_live.json` 最多只剩 1 筆交易。**月報、勝率、% 報酬全部失真**。

**根因**：日盤 server（port 8888）和夜盤 server（port 8889）兩個獨立 process，但都寫同一個 `data/performance/daily/{today}_live.json`。`PerformanceTracker._save_incremental` 用 `open(path, "w") + json.dump(self.today_trades)` 整檔覆寫，每個 tracker 只記得自己的交易 → last writer wins。`_save_daily`、`_update_cumulative`、`_generate_weekly`、`_generate_monthly` 全部同樣 race。

**修法**：`core/performance.py:PerformanceTracker.__init__` 依 `DASHBOARD_PORT` 計算 `self._suffix = "_night" if port=="8889" else ""`，13 處檔案路徑全部套用。完全比照 `risk/persistence.py:_state_file()` 的模式。
**Why:** 兩個 process 共用一個檔案但各自整檔覆寫 = 同一類 race condition，跟 risk_state 的 bug 是同個故事。  
**How to apply:** 之後若要看「實際成交了什麼」，只信 engine log 的 `_execute_entry` / `_execute_exit_inner`，不信 daily journal（5/4 之前的歷史已用 backfill 補回）。新檔案結構：日盤 `{date}_live.json`、夜盤 `{date}_live_night.json`，cumulative 也分 `cumulative.json` / `cumulative_night.json`。

## ④ 5/5 09:01 +1,920 紀錄調查（**真 bug = 已於 5/5 09:05 修復、但無法回補**）

User 質疑「實際利潤比 1,920 多」。查 engine log + 對照 [2026_05_05_fixes.md] 後完整真相：

- 05:09 起 `KbarPoller TMF synthetic tick: 40800` 持續 4 小時（Solace 斷線，REST 卡住）
- 08:50 進場 @ 40853，**`_entry_atr=14pt`** 寫入策略 instance 記憶體
- 08:51-08:57 連續 6 分鐘 stale price 40855
- **08:57:49 watchdog 重啟 server → `_entry_atr` 歸零**
- 08:57:51 重啟後 trail 計算 fallback 到 `snapshot.atr=53pt`（**3.8 倍** 進場 ATR）
- trail_trigger 從 14pt 變成 53pt、trail_dist 從 17.5pt 變成 66pt
- 09:01:52 真實價格 40964（+3,330 unrealized）
- 09:01:59 trail 觸發 @ 40,922（+69pt = +207pts × 10 − 150 commission = **+1,920 net**）
- **09:05:19 修復**：`core/position.py` + `core/engine.py` 加入 `strategy_state` 持久化（`_entry_atr` / `_trail_best` / `_breakeven_active` / `_scaled_out` 寫入 position JSON、30s 節流、重啟恢復）

**真正的 bug**：進場 ATR 沒持久化 → 重啟後用市場當下 ATR fallback（瞬時放大 3.8 倍）→ trail_dist 暴增 → 過早出場吃掉利潤。  
**Why:** 我（2026-05-06）一開始的分析只看到「stale price」這層皮，沒查 [2026_05_05_fixes.md]。memory 早就寫了 "trail 過早觸發出場 @ 40,922（+69pt），本應持有更久" — 這筆 trade 就是 5/5 修復的觸發點。  
**How to apply:** 「實際利潤比紀錄多」這句 user 質疑 → 直接看 [2026_05_05_fixes.md]「Bug 2」章節，不要重新分析。修復針對「下次重啟不再發生」，已平倉的 trade 損失無法回補。journal 維持 +1,920 是事實成交記錄。

**仍未根治的次要 bug**：KbarPoller 連續 REST timeout 時繼續 emit stale synthetic tick 給策略 — 雖然 _entry_atr 持久化已解決重啟後的 trail 計算錯誤，但 stale price 階段（重啟前的 6 分鐘）策略仍可能錯誤判斷。需要修 `core/broker.py:KbarPoller._poll` 連續 N 次 timeout 後停止 emit。
