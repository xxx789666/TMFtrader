## Bug 1 — [Scan] watchdog 誤報（`strategy/breakout.py`）

**根因**：進場後 `_cooldown_bars = 5`，冷卻期 early return（line 151）在 `[Scan]` log（line 164）之前 → 進場後 25 分鐘無 `[Scan]` → watchdog 12 分鐘超時誤報 TG。

**修復**：將 `in_day/in_night` 計算和 `[Scan]` log 移到冷卻期 early return **之前**，確保每根 K 棒無論狀態都記錄。

**注意**：watchdog 偵測到持倉時已會跳過重啟（line 509-510），只是 TG alert 仍會發。修復後不再誤報。

## Bug 2 — KbarPoller fallback stale price（`core/broker.py`）

**根因**：Solace 斷線後 KbarPoller 使用 `_last_real_tick_price`（凍結值），TP/SL/Trail 評估用 stale price → 今日 TP 40,551 在市場到達 40,561 時未觸發。

**修復**：fallback 時先用 `concurrent.futures.ThreadPoolExecutor` 帶 **5s timeout** 呼叫 `api.snapshots([contract])`：
- 成功 → 用 REST 真實價格，同時更新 `_last_real_tick_price`
- timeout/失敗 → 降級使用 stale price（原本行為）

**位置**：`broker.py` `_start_kbar_poller()` 內 fallback section。

## Bug 3 — TP 從未被引擎檢查（`core/engine.py`）【最嚴重】

**根因**：
1. `engine.py` 的 hard check 只有 SL（`tick.price <= pos.stop_loss`），**無 TP 檢查**
2. `strategy/breakout.py` 的 `check_exit()` 也從未讀取 `position.take_profit`
3. `take_profit` 欄位只用於「設定信號時傳入」，實際出場邏輯完全依賴 trail stop

**影響**：TP 價位完全形同虛設，即使 Solace 正常連線也無法靠 TP 出場。今日 TP 40,551 被突破後沒有出場，直到人工發現並三次重啟後才由修復後的 hard TP 出場 @ 40,648。

**修復**：`engine.py` `_process_tick()` 加入 hard TP check，與 hard SL 平行執行：

```python
# 每個 Tick 都執行（_process_tick）
if pos.take_profit > 0:
    if pos.side == Side.LONG and tick.price >= pos.take_profit:
        hard_tp_hit = True
    elif pos.side == Side.SHORT and tick.price <= pos.take_profit:
        hard_tp_hit = True

if hard_tp_hit:
    → Signal(reason=f"硬停利 @ {tick.price:.0f}（停利價 {pos.take_profit:.0f}）", source="hard_tp")
    → self._execute_exit(...)
```

**位置**：`engine.py` line ~882，`_process_tick()` 方法內。

## 教訓

1. **TP 必須在 engine 層 hard check**，不能只靠策略的 `check_exit()`。策略 check_exit 是「軟」出場邏輯，可能在異常狀態（ATR=0、restart 後 entry_atr 重置）下失效。
2. **KbarPoller stale price** 會讓引擎在 Solace 斷線期間完全「瞎眼」，即使 REST API 有真實數據也不用。
3. 持倉 state 儲存在 `data/state/paper_pos_TMF.json`，重啟自動恢復（`PositionManager.restore_positions()`）。
